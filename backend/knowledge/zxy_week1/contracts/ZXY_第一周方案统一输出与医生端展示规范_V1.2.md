# 1. 文档定位

本文件仅定义 **AI 方案生成结果如何在 Codex 网页中以固定结构展示**，不修改 A–F 分型、能量计算、饮食生成、运动处方、肺预康复、安全规则、周复评等临床生成逻辑。

原则：

1. 01/02/03 继续负责“方案怎么生成”。
2. 本文件负责“生成结果怎么稳定显示”。
3. 所有患者（A/B/C/D/E/F）使用相同的一级模块、顺序和标题。
4. 不允许因为某位患者某模块内容少，就删除一级模块或改变后续序号。
5. 页面标题、模块顺序、中文标签由前端固定，不由大模型自由生成。
6. 英文枚举、内部 ID、状态码可在后台保留，但医生端优先显示中文。
7. 医生端和患者端可读取同一份核心方案数据；医生端额外显示审核、修改、发布等治理信息。
8. 审核/治理状态应集中显示，避免在 Day1–Day7、每餐、每个动作中反复出现“待审核/待确认”。
9. 临床内容模块优先展示“患者实际要吃什么、做什么”；发布资格、待确认事项和阻断原因统一收敛到第11模块。
10. 必须区分“临床目标是否已确认”与“菜单营养值能否由合法数据直接计算”，二者不得混为一谈。

## 1.1 审核状态去重复原则

### 方案级状态
- `AI_GENERATED_PENDING_REVIEW / IN_REVIEW / APPROVED_PENDING_PUBLISH / PUBLISHED` 作为治理状态，优先显示在模块1顶部状态卡和模块11。
- 不要求在每个模块重复“待审核”。

### 目标级状态
- 能量、蛋白等临床目标若为 `PROVISIONAL`，医生端内容区优先显示为 **候选**，例如：`约1560 kcal/日 [候选]`。
- `ACTIVE` 显示为 **已确认**。
- `UNAVAILABLE` 显示为 **暂无法形成精确目标**。
- 目标状态通常在模块4显示一次；除非某个模块存在与总状态不同的例外，不在 Day1–Day7 反复重复。

### 菜单营养计算值
- 若食材来源合法、最终执行量已 materialize、营养数据可用且重算完成，则每日菜单 kcal / 蛋白 / 碳水 / 脂肪属于**菜单计算值**，可以直接显示。
- 菜单计算值不因为能量目标为 `PROVISIONAL` 就自动加“待审核”。
- 若存在 `PENDING_MDT / NEEDS_SOURCE_RECALC / NEEDS_RECALC` 等导致无法完成可靠定量计算，应显示 **营养汇总暂不显示 / 待重算 / 来源待确认**，而不是写“精确 kcal/蛋白待审核”。

### 运动与肺预康复剂量
- 若本周运动或肺预康复剂量整体处于候选状态，在模块顶部显示一次 **本周剂量：候选** 即可。
- 同一状态不在每个动作后重复“待审核/待确认”；仅对状态不同或存在特殊 blocker 的项目单独标注。

### 发布治理
- 第11模块集中显示：当前方案状态、发布资格、待确认事项、真实发布阻断项、审核意见和操作按钮。
- **黄色安全等级本身不自动等于发布阻断。** 黄色可导致自动进阶冻结、需要医护复核或某些任务降阶；只有具体未满足的发布条件才列入“当前阻断项”。

# 2. 固定一级结构

所有第一周方案统一固定为以下 11 个一级模块：

1. 患者关键画像与当前管理状态
2. 综合评估结果
3. 本周管理目标
4. 能量与营养依据
5. 第一周饮食方案
6. 第一周运动方案
7. 第一周肺预康复
8. 监测与记录
9. 安全规则 / 暂停与升级条件
10. 第7天周复评 / 下一周计划
11. 医护审核与发布

一级标题由前端写死，不由 AI 输出编号。

# 3. 一级模块详细字段

## 3.1 患者关键画像与当前管理状态

### 目标
让医生在 20–30 秒内理解“这个患者为什么得到下面这套方案”。

### 固定展示字段
- 患者姓名
- 患者 ID / 病例号（次要显示）
- 性别
- 年龄
- 当前管理阶段
- 距预计手术时间
- 当前方案周期（如：术前第1周）
- 当前方案状态（如：待审核）
- 身高
- 体重
- BMI
- 腰围
- 体脂率
- SMI / 骨骼肌等关键体成分（如有）
- 近期体重趋势
- 食欲 / 摄入状态
- 主要疾病 / 代谢问题
- 主要症状
- 6MWT
- BORG
- SpO₂ 变化
- 当前运动基础
- 运动限制
- 家庭支持
- 执行障碍
- 饮食记录方式
- 运动偏好

### 显示规则
- 页面主要显示患者姓名，不显示测试 Case ID 作为主名称。
- `SYN-A01` 等仅作为测试/病例编号，可在姓名下方次要显示。
- 不把完整患者档案全部搬入本页，仅显示与方案决策直接相关的关键项。
- 空值不显示“正常”，应显示“未提供 / 待补充”。

## 3.2 综合评估结果

### 固定展示字段
- 主营养表型：A / B / C / D / E
- F complexity overlay：有 / 无
- display phenotype（后台保留，可不直接显示）
- 当前安全等级：绿色 / 黄色 / 红色
- 方案优先方向
- 主要判定依据
- 是否允许减脂
- 是否营养恢复优先
- 是否需要保肌优先
- 是否需要功能优先
- 是否需要执行简化
- 当前自动进阶资格

### 前端推荐显示

示例：

- 主表型：A型
- 复杂度叠加：无
- 安全等级：绿色
- 主要方向：减脂同时保肌
- 判定依据：高体脂、体重稳定、摄入正常、功能允许、无明显运动限制
- 自动进阶：本周不自动进阶

### F overlay 规则
若存在 F，必须同时显示底层主表型。

示例：

> 主表型：B型  
> 复杂度叠加：F  
> 主要方向：代谢控制 + 保肌 + 执行简化

禁止只显示“F型”而丢失 underlying A–E 方向。

## 3.3 本周管理目标

固定分为以下 5 个子项：

### ① 营养 / 体重目标
例如：
- 适度减脂，不追求快速下降
- 停止继续下降，优先恢复摄入
- 维持体重，保护肌肉

### ② 肌肉 / 功能目标
例如：
- 减脂同时保肌
- 保持下肢功能
- 改善活动耐量
- 避免术前去体能

### ③ 运动目标
例如：
- 正式有氧 4 天
- 抗阻 3 天
- 功能活动每日按需
- 本周不自动进阶

### ④ 肺预康复 / 术前准备目标
例如：
- 学会缩唇呼吸
- 学会腹式呼吸
- 完成必要术前技能熟悉
- 无指征项目不机械增加

### ⑤ 本周注意事项
推荐固定显示为自然语言：

> 不追求快速减重；不跳餐补偿；若短期体重变化不明显，不自行进一步减少饮食量或增加运动量。

注意：本模块表达“本周管理方向”，不要重复具体每日处方。

## 3.4 能量与营养依据

### 医生端固定展示字段
- 当前能量目标 / 候选目标（如有）
- 能量目标状态
- 计算依据
- REE / BMR
- PAL
- TEE
- 表型调整比例
- 蛋白目标 / 候选目标（如有）
- 蛋白目标状态
- 碳水供能范围（如适用）
- 当前菜单营养计算状态（已计算 / 待重算 / 不形成定量闭合）

### 中文显示规则

后台：`PROVISIONAL`  
医生端内容区：**候选**

后台：`ACTIVE`  
医生端内容区：**已确认**

后台：`UNAVAILABLE`  
医生端内容区：**暂无法形成精确目标**

后台：`EXACT_PROVISIONAL_REVIEW`  
医生端不直接显示工程枚举，可显示：**按候选目标生成**

后台：`EXACT_ACTIVE`  
医生端可显示：**按已确认目标生成**

后台：`STRUCTURE_ONLY`  
医生端可显示：**仅生成饮食结构，不形成精确能量目标**

后台：`P3_BIA_BMR_TEMP`  
医生端可显示：**BIA/BMR + 活动系数 + 当前表型策略**

### 推荐示例
> 能量候选目标：约 1560 kcal/日 `[候选]`  
> 计算依据：BIA/BMR 1360 kcal × PAL 1.35 → TEE 约 1836 kcal，再按 A 型候选策略调整  
> 蛋白候选目标：约 82 g/日 `[候选]`  
> 菜单营养计算：已完成，可在每日方案中直接显示菜单计算值

### 显示原则
- **候选目标状态与菜单营养计算值必须分开。**
- 临床目标为 `PROVISIONAL` 时，只需在本模块或模块顶部标记一次“候选”，不在 Day1–Day7 重复“待审核”。
- 若菜单使用的食材来源、最终执行克重及营养数据均满足计算条件，kcal / 蛋白 / 碳水 / 脂肪应作为“菜单计算值”直接显示。
- “目标尚未正式确认”不等于“菜单营养值算不出来”。
- 若营养来源未确认或需要重算，不显示伪精确数值；使用“营养汇总暂不显示 / 待重算 / 来源待确认”等准确状态。
- 发布资格、待确认事项和发布阻断不在本模块重复展开，统一在模块11集中展示。
- 计算链可折叠显示，默认展示关键结果。
- 技术状态码保留后台，不作为医生端主要文案。

## 3.5 第一周饮食方案

### 顶部固定“本周饮食摘要”
- 餐次结构
- 当前能量方向 / 候选目标（状态只在顶部显示一次）
- 蛋白方向 / 候选目标（状态只在顶部显示一次）
- 菜单营养计算状态
- 饮食总体原则
- 主要行为重点
- 特殊症状策略（如适用）
- 是否需要营养恢复
- 是否使用 ONS（仅在已有明确审核/ACTIVE依据时显示具体产品与剂量）

### Day1–Day7 固定折叠结构
默认展开 Day1，Day2–Day7 折叠。

每一天固定包括：
- 早餐
- 上午加餐（如有）
- 午餐
- 下午加餐（如有）
- 晚餐
- 当日营养汇总（如可计算）
- 当日特殊提醒

### 每餐固定包括
- 菜品 / 食物名称
- 最终可执行份量
- 食材
- 烹调方式（必要时）
- kcal / 蛋白 / 碳水 / 脂肪（医生端可显示）
- 替换方案
- 特殊症状下调整方式

### 当日营养汇总显示规则

**A. 可以可靠计算时：**

直接显示：

> 当日菜单计算值：能量 xxxx kcal｜蛋白质 xx g｜碳水 xx g｜脂肪 xx g

不再追加“待审核”。

**B. 不能可靠计算时：**

根据真实原因显示：

- 营养汇总暂不显示
- 待重算
- 食材来源待确认
- 当前为 STRUCTURE_ONLY，不形成定量营养闭合

禁止用笼统的：

> 精确 kcal/蛋白待审核

替代真实计算状态。

### 显示原则
- 患者端不以 `C004 / P003 / V012` 等组件 ID 为主要显示。
- 医生端可将组件 ID 放在次要信息或折叠区。
- 不允许“加餐后再补一份”等会造成计划外叠加的表达。
- 替换后若涉及营养闭合，应提示需重新计算。
- Day1–Day7 内容必须分别独立展开，不使用“同前”“同Day2”。
- 能量/蛋白“候选”状态在顶部或模块4标记一次即可，不在每一天重复。
- 患者可见内容优先显示菜名 + 最终食材克重/容量/个数 + 简单做法。

## 3.6 第一周运动方案

### 顶部固定“周结构摘要”
- 正式有氧：X 天
- 功能活动：X 天
- 抗阻：X 天
- 柔韧 / 恢复：X 天
- 当前运动安全等级
- 是否允许自动进阶
- 是否存在降阶 / 简化
- 本周剂量状态（如整体为候选，仅在此处显示一次）

### 剂量状态展示原则
- 若本周大多数运动剂量均为同一 `PROVISIONAL` 状态，顶部显示 **本周剂量：候选** 即可。
- Day1–Day7 的动作卡直接显示实际分钟、次数、组数和替代方案，不逐条重复“待审核/待确认”。
- 只有某个动作状态与本周总体状态不同、存在特殊限制或被单独阻断时，才在该动作旁单独标记。

### Day1–Day7 固定折叠结构
每一天固定包括：
- 正式有氧
- 功能活动
- 抗阻
- 柔韧 / 恢复
- 当日注意事项
- 替代方案
- 停止条件

### 每个动作卡固定显示

#### 第一层：本患者本周实际处方
示例：
- 快步走：15分钟 × 1次
- 墙壁俯卧撑：8–12次 × 1–2组

#### 第二层：知识库参考范围
可折叠显示：
- 参考范围：15–45分钟，4–5次/周

### 强制规则
- “本周实际处方”与“知识库参考范围”必须视觉分开。
- 正式有氧和功能活动必须区分。
- 不允许把日常轻走自动算成正式有氧。
- 若正式有氧为 0 天，模块仍必须存在，并显示原因。
- 若动作因疼痛、安全、执行困难而减少，应显示简化原因。

## 3.7 第一周肺预康复

### 顶部固定“本周选择逻辑”

> P03/P04 暂无明确需要  
> P05 无痰 / 无排痰困难时不固定安排  
> P06 无设备 / 无医护处方时不安排

### 固定展示字段
- 本周剂量状态（如整体为候选，仅显示一次）
- 选中的肺预康复项目
- 项目名称
- 本周实际剂量
- 目的
- 操作要点
- 频率
- 停止条件
- 未选项目及原因
- 条件性项目触发条件

### 显示原则
- 若所选肺预康复剂量整体为候选状态，在模块顶部显示一次 **本周剂量：候选**；不在每个 P01/P02/P03/P04 动作后反复写“待审核”。
- 不以“项目越多越完整”为目标。
- P05 / P06 必须按照现有 gate 规则显示。
- 无项目时仍保留模块，并显示“本周无新增肺预康复任务 + 原因”。

## 3.9 安全规则 / 暂停与升级条件

### 顶部固定状态卡
- 当前安全等级
- 当前黄色触发项
- 当前红色触发项
- 营养方案：允许 / 冻结
- 减脂方向：允许 / 冻结
- 正式有氧：允许 / 降阶 / 暂停
- 抗阻：允许 / 降阶 / 暂停
- 肺预康复：允许 / 降阶 / 暂停
- 自动进阶：允许 / 冻结

### 黄色条件
前端显示为：

> 暂停自动进阶 → 优先处理原因 → 保留安全基础任务 → 同步医护复核

### 红色条件
前端显示为：

> 立即停止相关任务 → 转医护 / 急症流程 → 红色解除需医护确认

### 原则
- 不允许 AI 自行创造 HR / BP / SpO₂ / 血糖等具体停止阈值。
- 若院内阈值未配置，应显示“按医护设定阈值执行”。

---

## 3.10 第7天周复评 / 下一周计划

### 第一周尚未执行完成时
显示：

- 复评状态：尚未到复评时间
- 计划复评时间：Day7
- 待评价指标：体重趋势、饮食完成度、运动完成度、症状、BORG、疲劳恢复等

不要在患者尚未执行时显示：
“本周决策：数据不足”

### Day7 后允许显示的中文结论

后台枚举 → 医生端中文：

- `MAINTAIN` → 维持当前方案
- `BARRIER_FIRST` → 优先解决执行障碍
- `PRESERVE_MUSCLE` → 优先保肌
- `NUTRITION_RECOVERY` → 优先营养恢复
- `DEINTENSIFY` → 适当降低干预强度
- `SAFETY_REVIEW` → 安全复核
- `INTENSIFY_CANDIDATE` → 可考虑小幅进阶
- `DATA_INSUFFICIENT` → 数据不足，暂不调整

### 显示规则
- 医生端主要显示中文。
- 英文枚举仅后台保留。
- 下一周建议必须基于实际执行和监测数据，不得仅按 A–F 标签自动决定。

## 3.11 医护审核与发布

### 固定显示字段
- 当前方案状态
- 当前发布资格
- 待确认事项
- 当前发布阻断项
- 当前安全等级（单独显示，不与发布阻断混为一项）
- 自动进阶状态
- AI生成时间
- 最近修改时间
- 方案版本
- 审核医生
- 审核意见
- 退回原因（如有）

### 展示原则
- 本模块是治理信息的**集中入口**。
- 模块4–7已经显示过的“候选目标/候选剂量”，在这里可汇总成待确认事项，但不要求前面每个条目重复“待审核”。
- “当前发布阻断项”只列真正导致不能发布的条件，例如：必需目标未确认、关键 ACTIVE 配置缺失、validator FAIL、存在未解决的安全 blocker 等。
- **黄色安全等级本身不自动写入发布阻断项。** 应单独显示黄色触发原因及其造成的后果，例如“自动进阶冻结 / 某任务降阶 / 需医护复核”。
- 若黄色状态下所有正式发布条件已经满足，可由既有 publication gate 决定是否允许发布，不在 UI Contract 中额外创造“黄色=禁止发布”的规则。

### 固定操作按钮
- 编辑方案
- 添加审核意见
- 退回修改
- 审核通过
- 发布给患者

### 发布原则
只有满足平台既有发布闭环后，才能转为 PUBLISHED。

医生端无需单独再设“待补充资料”一级模块；所有需补资料、需确认参数、真正阻断发布的事项统一收敛到本模块。

# 5. 空值与缺失数据规则

统一处理：

- 明确没有 → 显示“无”
- 患者未提供 → 显示“未提供”
- 当前不适用 → 显示“不适用”
- 需要人工确认 → 显示“待确认”
- 尚未到复评时间 → 显示“尚未到复评时间”
- 后台 null 不得自动翻译成“正常”
- 缺失不等于阴性
- 缺失不等于无需处理

# 8. Codex 页面验收标准

完成后至少满足：

1. A/B/C/D/E/F 六类患者均显示完全相同的 11 个一级模块。
2. 一级标题顺序固定。
3. 某模块无内容时不删除模块，而显示“不安排 / 不适用 / 待确认 + 原因”。
4. 医生端不直接暴露难懂的英文工程状态作为主要文案。
5. `PROVISIONAL` 在临床内容区优先显示为“候选”，不要求每个条目重复“待审核”。
6. 候选能量/蛋白目标在模块4或模块顶部清晰标记一次即可。
7. 若菜单营养值已满足合法食材来源 + 最终执行量 + 营养重算条件，应直接显示每日“菜单计算值”，不追加“待审核”。
8. 若菜单营养值不能可靠计算，应显示“暂不显示 / 待重算 / 来源待确认 / STRUCTURE_ONLY”，不得笼统写“精确 kcal/蛋白待审核”。
9. 运动或肺预康复若整体为候选剂量，模块顶部显示一次即可；动作卡不重复相同审核文案。
10. 运动“本周实际处方”和“知识库参考范围”必须分开。
11. 正式有氧与功能活动必须分开计数。
12. Day1–Day7 默认 Day1 展开，其余折叠。
13. Day1–Day7 不使用“同前 / 同Day2”。
14. 安全等级和暂停/升级条件始终可见。
15. 黄色安全等级与“发布阻断”分开显示；黄色本身不得被前端自动翻译为“不可发布”。
16. 第一周尚未执行完时，周复评显示“尚未到复评时间”，而不是“数据不足”。
17. 所有待确认事项、真正发布阻断项和审核意见统一收敛到“医护审核与发布”。
18. “待补资料”不再单独占一级模块。
19. 医生端保留“编辑方案 / 添加审核意见 / 退回修改 / 审核通过 / 发布给患者”。
20. Patient View 与 `plan_view` 必须来自同一核心方案数据，不允许通过解析 AI 自由 Markdown 标题来决定模块归属。
21. 页面结构变化不得反向修改 01/02/03 临床规则文件。

# 10. 最终原则

> **临床规则负责“生成什么”，UI Contract 负责“怎么稳定展示”。**

> **患者不同，内容不同；页面结构不变。**

> **后台保留机器字段，医生端显示临床可读中文。**

> **医生审核时首先看到本患者真实方案，而不是工程状态码。**

> **审核状态集中、临床内容展开：候选目标标一次，可计算结果直接显示，真正待确认事项统一进入第11模块。**
